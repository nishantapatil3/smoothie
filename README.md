# Smoothie

A privacy-first, **fully local** audio transcription + summarization service.
Modeled on [meetily](https://github.com/Zackriya-Solutions/meetily), but with a
**Python backend** and **whisper.cpp** for on-device transcription.

- 🎙️ Clients (web first) upload audio recordings
- 🔊 Transcription runs **locally** via `whisper.cpp` (Apple Metal, NVIDIA CUDA, AMD Vulkan/ROCm, or CPU)
- 🧠 Summaries are generated by a **summarizer LLM** reached through a generic
  OpenAI-compatible API endpoint — you point it at any server that speaks
  `/chat/completions` (local or remote)
- 🗄️ Everything is stored in a local **SQLite** database — no cloud required

## Architecture

```
 Web UI (React+Vite)  ──HTTP──▶  FastAPI backend (:5173)
                                       │
                          ┌────────────┴────────────┐
                          ▼                         ▼
                    whisper.cpp              Summarizer LLM
                  (local transcription)   (OpenAI-compatible API endpoint)
                          └────────────┬────────────┘
                                       ▼
                              SQLite (recordings,
                              transcripts, summaries, jobs)
```

Upload → enqueue async job → transcribe → summarize → persisted. The client polls
`GET /api/recordings/{id}` until the status is `completed` or `failed`.

## Requirements

- macOS, Linux, or Windows (CPU baseline; GPU support depends on the installed native build)
- FFmpeg available on `PATH` (e.g. `brew install ffmpeg` on macOS)
- Python 3.10+ (developed on 3.12)
- Node.js 18+ (for the web UI)

## Quick start

### 1. Backend

```bash
cd backend
python3.12 -m venv .venv
source .venv/bin/activate
pip install -e .
uvicorn smoothie.main:app --reload --port 5173
```

The backend uses the system certificate store for Hugging Face access,
including enterprise proxy certificates.

Alternatively, run the backend directly with Python:

```bash
python smoothie/main.py
```

The first run downloads the Whisper model from HuggingFace (cached afterwards).

### GPU acceleration

Smoothie uses [pywhispercpp](https://github.com/absadiki/pywhispercpp) bindings.
`transcription_device: auto` lets whisper.cpp discover a GPU supported by the
installed build and fall back to CPU. It does not install GPU drivers or add
backends to an existing CPU build. The native startup logs identify the device.
Set `transcription_device: cpu` in Settings to force CPU inference.

For accelerated source builds, install the relevant SDK/toolkit, CMake, and a
C++ compiler first. Run the appropriate command inside the backend virtualenv:

```bash
# Apple Silicon: build with Metal
CMAKE_ARGS="-DGGML_METAL=ON" pip install --force-reinstall --no-cache-dir --no-binary=pywhispercpp 'pywhispercpp==1.5.1'

# NVIDIA: requires the CUDA toolkit
GGML_CUDA=1 pip install --force-reinstall --no-cache-dir --no-binary=pywhispercpp 'pywhispercpp==1.5.1'

# AMD (or other Vulkan-capable GPU): requires the Vulkan SDK and drivers
GGML_VULKAN=1 pip install --force-reinstall --no-cache-dir --no-binary=pywhispercpp 'pywhispercpp==1.5.1'

# AMD ROCm: requires a supported GPU and ROCm/HIP toolchain
CMAKE_ARGS="-DGGML_HIP=ON" pip install --force-reinstall --no-cache-dir --no-binary=pywhispercpp 'pywhispercpp==1.5.1'
```

These shell examples use POSIX syntax; on Windows, set the corresponding build
variables in your shell before invoking pip. Backend support follows the
[whisper.cpp build requirements](https://github.com/ggml-org/whisper.cpp).

Model names such as `tiny`, `small`, `large-v3-turbo`, and `small-q8_0` download
the corresponding `ggml-*.bin` file from `ggerganov/whisper.cpp` into the Hugging
Face cache. A local `.bin` file can be configured instead. Existing standard
`mlx-community/whisper-...` model names migrate to the same model size; weights
are downloaded again in whisper.cpp format. Local MLX directories must be
replaced with a whisper.cpp `.bin` file.

### 2. Web UI (dev mode)

```bash
cd webui
npm install
npm run dev        # http://localhost:5174  (proxies /api -> :5173)
```

Open http://localhost:5174, record or upload audio, and watch the transcript +
summary appear.

### First run / accounts

Smoothie is multi-user. On first open the web UI shows a login screen — click
**"Need an account? Register"** to create the first account. Set a stable
`auth_secret` in `config.yaml` (e.g. `openssl rand -hex 32`) so issued tokens
survive backend restarts; without it an ephemeral secret is generated each boot
and you will be logged out on restart.

> **Upgrading an existing database:** pre-auth recordings had no owner. The
> `user_id` column is added automatically, but those legacy rows keep an empty
> owner and are hidden from all accounts. Start fresh (or re-import) for a
> fully-owned library.

### Single-process production mode

Build the UI, then run only the backend — it serves the built UI at `/`:

```bash
cd webui && npm run build && cd ../backend
source .venv/bin/activate
uvicorn smoothie.main:app --port 5173
# open http://localhost:5173
```

## Development & tests

Install the backend with the `dev` extra (adds `pytest`), then run the test suite:

```bash
cd backend
source .venv/bin/activate
pip install -e ".[dev]"
pytest
```

Unit/API tests run without downloading model weights. To include the native
long-speech integration tests (macOS `say`, FFmpeg, and ffprobe required):

```bash
SMOOTHIE_INTEGRATION_TESTS=1 pytest tests/test_chunking.py
```

The test suite pins key behaviors:

- `backend/tests/test_trim.py` — regression guard that silence trimming keeps
  **all** speech in order (`stop_periods=-1`); a known regression
  (`stop_periods=1`) would drop everything after the first spoken chunk.
- `backend/tests/test_progress.py` — job progress / status transitions.

## Configuration

All settings live in **`backend/config.yaml`** (YAML), the single source of
truth — there are no environment variables. A fully-commented template is at
`backend/config.yaml.example`; copy it to `config.yaml` and adjust, or just let
the server create one on first save. **`config.yaml` is git-ignored** (it can
hold secrets like `summary_key` / `auth_secret`); only `config.yaml.example` is
committed.

The web UI has a **Settings** page (⚙ in the header) that reads and edits every
setting live — changes apply immediately and are written back to `config.yaml`.
`auth_secret`, `data_dir`, and `ffmpeg_bin` are **not** exposed in the UI
(secret / database-stability); set those directly in `config.yaml`.

| Setting | Default | Purpose |
| --- | --- | --- |
| `host` | `0.0.0.0` | Bind address for the backend server |
| `port` | `5173` | Port the backend listens on |
| `job_poll_interval` | `2.0` | Background job loop polling interval (seconds) |
| `auth_secret` | _(ephemeral)_ | Secret signing access tokens (HMAC). Set a stable random value so tokens survive restarts |
| `auth_access_ttl_minutes` | `60` | Access token lifetime in minutes (refreshed silently) |
| `auth_refresh_ttl_days` | `7` | Refresh token lifetime in days (rotated on each use) |
| `auth_min_password_len` | `8` | Minimum password length at registration |
| `transcription_model` | `large-v3` | whisper.cpp model name, quantized name, or local ggml `.bin` file |
| `transcription_device` | `auto` | Use an available compiled GPU backend, falling back to CPU; `cpu` disables GPU inference |
| `transcription_gpu_device` | `0` | Native GPU index used in automatic mode |
| `transcription_language` | `en` | Force a language code, or empty for auto-detect |
| `summary_url` | `http://localhost:11434/v1` | OpenAI-compatible `/chat/completions` base URL |
| `summary_key` | _(empty)_ | Optional bearer token for the endpoint |
| `summary_model` | `llama3.2` | Model name to request from the summarizer LLM |

### Pre-audio-processing (pluggable modules)

Before transcription, audio passes through a chain of **enable/disable-able
modules** (`backend/smoothie/preprocess/`). Each module is independently
configured; a module that fails falls back to its input so a misconfigured
filter never breaks a job. Add a module by implementing `AudioProcessor` (audio
transform) or `TranscribeTuner` (Whisper options) and registering it.

| Setting | Default | Purpose |
| --- | --- | --- |
| `ffmpeg_bin` | _(auto-detect)_ | Path to the `ffmpeg` binary |
| `trim_enabled` | `false` | Trim silence before transcription |
| `trim_threshold` | `-40` | Noise floor (dB) treated as silence |
| `trim_min_silence` | `0.5` | Min silent stretch (s) to cut |
| `tune_enabled` | `true` | Surface Whisper decode options |
| `tune_beam_size` | _(unset)_ | `beam_size` (None = greedy, like meetily) |
| `tune_condition_on_previous_text` | _(unset)_ | Feed prior text into next window |
| `tune_no_speech_threshold` | _(unset)_ | Silence-vs-speech cutoff |
| `vad_enabled` | `true` | Split long audio at speech pauses (meetily-style) instead of fixed windows |
| `vad_threshold` | `0.5` | Silero speech probability threshold |
| `vad_min_speech_ms` | `250` | Ignore sounds shorter than this |
| `vad_min_silence_ms` | `400` | Pause length that ends a chunk run |
| `vad_speech_pad_ms` | `200` | Pad each run so onsets/tails aren't cut |
| `vad_chunk_target_sec` | `24` | Target merged chunk length (~meetily 22-27s) |
| `vad_chunk_max_sec` | `30` | Hard cap on a single chunk |

The `tune` module maps beam size, prior-text context, and no-speech threshold
into whisper.cpp decoding parameters. It enables native non-speech token
suppression and greedy `best_of=2`; temperature fallback uses whisper.cpp's
defaults. The old `tune_hallucination_silence_threshold` setting is ignored on
upgrade because whisper.cpp has no equivalent parameter.

**Long recordings are transcribed in bounded windows.** When VAD is enabled,
speech is grouped into chunks of up to 30 seconds. Otherwise, fixed 30-second
windows with a one-second overlap are used. Each chunk is decoded independently,
then text and timestamps are merged and progress is reported. Short recordings
are transcribed in one pass.

The `trim` module removes silence **throughout** the recording (`stop_periods=-1`
in ffmpeg), preserving all speech in order. Using `stop_periods=1` is a known
regression: it keeps only the first spoken chunk and discards the rest of a long
recording. A regression test in `backend/tests/test_trim.py` pins this.

### Enabling summaries

The backend talks to **one** OpenAI-compatible endpoint — the summarizer LLM.
Point it wherever you want; it's your choice:

**Local summarizer LLM** (default, fully offline — e.g. a local OpenAI-compatible server):

```yaml
# summary_url defaults to http://localhost:11434/v1
```

**Remote / other endpoint** (OpenAI, vLLM, LM Studio, …) — set in `config.yaml`:

```yaml
summary_url: https://api.openai.com/v1
summary_key: "sk-..."
summary_model: gpt-4o-mini
```

The same code path handles all of them — there is no separate Ollama vs cloud mode.
You can also change these from the web UI **Settings** page without restarting.

## API

| Method | Path | Description |
| --- | --- | --- |
| `GET`  | `/api/health` | Server status + active model/provider (public) |
| `POST` | `/api/auth/register` | Create an account → returns `{ token, refresh_token }` |
| `POST` | `/api/auth/login` | Log in with `username`/`password` → `{ token, refresh_token }` |
| `POST` | `/api/auth/refresh` | Swap a `refresh_token` for a fresh `{ token, refresh_token }` (old one revoked) |
| `POST` | `/api/auth/logout` | Revoke a `refresh_token` for the authenticated user |
| `GET`  | `/api/auth/me` | Current user (requires Bearer token) |
| `GET`  | `/api/settings` | Current editable settings (requires Bearer token) |
| `PUT`  | `/api/settings` | Update settings live + persist to `config.yaml` (requires Bearer token) |
| `POST` | `/api/recordings` | Upload audio (`multipart`: `audio`, optional `title`,`language`) — requires auth |
| `GET`  | `/api/recordings` | List **your** recordings (newest first) — requires auth |
| `GET`  | `/api/recordings/{id}` | Full detail: status, transcript, summary — requires auth, owner only |
| `GET`  | `/api/recordings/{id}/audio` | Download the original audio — requires auth, owner only |
| `DELETE` | `/api/recordings/{id}` | Delete a recording + its audio — requires auth, owner only |

All `/api/recordings*` routes require an `Authorization: Bearer <token>` header
issued by `/api/auth/login` (or `/api/auth/register`). Recordings are scoped to
the owning user — one user cannot see or fetch another's recordings.

**Token model (Ring-style).** Login/register return a short-lived **access
token** (default 60 min, `auth_access_ttl_minutes`) plus a longer-lived
**refresh token** (default 7 days, `auth_refresh_ttl_days`). When an
access token expires (API returns 401), the client calls `POST /api/auth/refresh`
with its refresh token to obtain a new pair — no re-login needed. Each refresh
**rotates** the refresh token (the old one is revoked), and `POST
/api/auth/logout` revokes it, so a leaked refresh token has a bounded lifetime
and can be invalidated. Refresh tokens are stored only as SHA-256 hashes in the
`refresh_tokens` table (never the raw value), so they remain valid across
restarts as long as `auth_secret` is stable.

Job statuses: `pending → transcribing → summarizing → completed` (or `failed`).

## Project layout

```
smoothie/
  backend/
    smoothie/         FastAPI app, whisper.cpp, summary providers, SQLite, preprocess modules
    config.yaml.example  Config template (copy to config.yaml)
    tests/            pytest suite (trim regression, progress/status, auth, settings)

```

## Out of scope (future iterations)

Speaker diarization, live/streaming transcription, mobile apps, multiple summary
styles, cloud sync. (Auth & multi-user accounts **are** supported — see above.)
